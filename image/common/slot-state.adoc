= slot-state
:persistent_dir: /persistent

Paths on the persistent partition are shown under the default mount point, `{persistent_dir}`. The image layout sets it with `IGconf_image_persistent_dir`.

== Mount points

[cols="1,3,1,4", options="header"]
|===
| Mount point | Backing | Type | Notes

| /home | {persistent_dir}/home | bind | User data shared across slots
| /var | {persistent_dir}/slots/<slot>/var | bind | Per‑slot runtime state (systemd, caches, etc.)
| /var/log/journal | {persistent_dir}/log/journal | bind | Single log directory used by both slots
| _<slot-shared paths>_ | {persistent_dir}/shared/<path> | bind | Application data shared across slots (layer-declared, see <<slot-shared>>)
|===

* **Rationale**
   ** Predictable per‑slot state in `/var`.
   ** Shared `/home` for slot agnostic user storage.
   ** Shared journalling: centralised point for device logging.

* **Logging**
   ** A single persistent journal directory at `{persistent_dir}/log/journal` stores logs from either slot.
   ** Journaling is configured for endurance and reliability.

* **Machine Identity (systemd)**
   ** `/etc/machine-id` is kept in `{persistent_dir}/common/etc/machine-id` with `EarlyPersistFile=`.

* **Offline updates (systemd)**
   ** Compatible with https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html#ConditionNeedsUpdate=[`ConditionNeedsUpdate=/etc`]. A rotation to a slot built with a newer `SOURCE_DATE_EPOCH` is an update of `/usr`.


[WARNING]
====
Slot partition GPT labels are mandatory to associate the immutable root with its matching persistent storage.

- Root slots must have stable PARTLABELs: e.g. `system_a` and `system_b`.
- At boot, a generator reads the root slot’s `PARTLABEL` to select `{persistent_dir}/slots/<slot>/var`.

If slot GPT labels are missing/duplicated, `/var` binding will fail.

If slot GPT labels can’t be guaranteed, this layout is not suitable for your device.
====


[[slot-shared]]
== Slot-shared application data

Any layer can declare filesystem paths whose application data should be shared across slots. At boot, each declared path is bind-mounted from a common location on the persistent partition so the same data is visible regardless of which slot is active.

=== Why /var is slot-local by default

Read literally, FHS supports sharing most of `/var` across slots: `/var/lib` is explicitly persistent per-host application state (unlike `/run`, which FHS separates out precisely because it is *not* meant to survive), and `/var/log`, `/var/spool`, and most software that keeps working state under `/var/lib` (NetworkManager, databases, container runtimes) expect that state to survive an upgrade.

But "survives an upgrade" and "survives a rollback" are different guarantees, and rollback is the reason this layout exists. State shared across slots can be written or migrated by a newer slot into a form the older slot's software cannot read. If a rollback then hits state it doesn't understand, the rollback - the main safety mechanism this A/B layout provides - is compromised.

Enumerating every `/var` path that is safe to share, and keeping that list correct as packages change what they write, is more failure-prone than making sharing an explicit, per-layer decision. Slot-local by default means a layer's on-disk state is simply absent/reset after a slot change unless the layer says otherwise. That makes the safe outcome the automatic one: a layer author who forgets to declare sharing ends up with reset state, not a silently shared state that a rollback can't read. Sharing is therefore opt-in, applied only where a maintainer has actually verified the application's state is safe (or required) to carry across slots - e.g. `machine-id` for identity stability, or NetworkManager's connection profiles and secret key for network continuity.

If you are writing a layer whose software keeps state under `/var` that users would reasonably expect to survive an update - credentials, device identity, accumulated data, long-lived queues - assume it will be wiped or reset on the next slot flip unless you add a `slot-shared.d` entry for it.

=== How it works

. At build time, every `/etc/rpi-image-gen/slot-shared.d/*.conf` file is compiled into `/usr/lib/rpi-image-gen/slot-state.manifest`. The device reads only the manifest.
. `slot-shared-generator` runs at early boot and emits a `.mount` systemd unit for each `SharedPath=` in the manifest, mounting `{persistent_dir}/shared/<path>` over `<path>` as a bind mount.
. `persistent-shared-init.service` runs before the bind mounts activate. It removes each `StaticPath=` from the shared location, then creates any missing `{persistent_dir}/shared/<path>` directories on the persistent partition and seeds them, handling first boot and disaster-recovery scenarios where the partition has been re-initialised.
. Bind mounts are guarded by `ConditionPathIsDirectory` on the source. If the directory is absent the mount is skipped and the service falls back to its local path - safe degradation with no boot failure.

=== Declaring a shared path

Drop a `.conf` file into `/etc/rpi-image-gen/slot-shared.d/`, eg via the layer's rootfs overlay or script:

[source]
----
Version=1
SharedPath=/var/lib/myapp
SharedPath=/etc/myapp/state
----

Every copy between the image, the device and persistent storage keeps a file's contents, ownership (by numeric ID), mode and modification time.

Each key other than `Version=` declares a VFS operation (vfsop) on a path.

`Version=1`:: Required. The format of the file. Any other value fails the build.
`SharedPath=`:: A directory shared across slots. `{persistent_dir}/shared/<path>` is bind-mounted over it, so every slot reads and writes the same data. Before the bind, files from the image that are missing there are copied in. Existing files are never overwritten, so changes made at runtime are kept. It must exist as a directory in the image. `SharedPath=` directories may be nested.
`Path=`:: The original name of `SharedPath=`, still accepted.
`StaticPath=`:: A file or directory inside a `SharedPath=` directory that the image owns rather than the device. The `SharedPath=` may be declared by any file. It is replaced from the active slot on every boot, so it always matches the running image, and anything written to it at runtime is discarded. If the image does not contain it, it is removed from the shared location.
`EarlyPersistFile=`:: A file under `/etc` kept in `{persistent_dir}/common` across boots and slot rotations. The initramfs restores the stored copy into an overlay on `/etc` with a tmpfs upper layer, so it is in place before switch-root. A stored copy takes precedence over the image's file, and the image's file is used until a copy is stored. It is saved back at boot, at shutdown and on `systemctl reload rpi-persist-files`. Deleting the file on the device does not remove the stored copy. It must not be inside a `SharedPath=` directory. Other writes to `/etc` succeed but are lost at reboot.

Each key may appear any number of times. Paths are absolute: a missing leading `/`, a trailing `/` and repeated `/` are corrected. A path must not contain whitespace, `.` or `..`, must not pass through a symlink in the image, and must not overlap the persistent directory. A path declared more than once with the same vfsop, by any files, is one entry. Declaring it with different vfsops, or using an unknown key, fails the build.

VFS operations are applied in a fixed order, whatever their order in a file: `EarlyPersistFile=`, then `StaticPath=`, then `SharedPath=`. Within each, paths are applied parents first.

For example, the device's SSH host keys are shared across slots, while the SSH configuration follows the active slot:

[source]
----
Version=1
SharedPath=/etc/ssh
StaticPath=/etc/ssh/sshd_config
StaticPath=/etc/ssh/sshd_config.d
----

The files are inert in non-AB configurations.

=== Persistent partition layout

Shared data is stored under `{persistent_dir}/shared/`, mirroring the full path hierarchy:

[source,subs="attributes+"]
----
{persistent_dir}/
└── shared/
    └── var/
        └── lib/
            └── myapp/    <-- bind-mounted over /var/lib/myapp
----

Because the immutable root retains a copy of each declared path, files baked into the image are pushed into the shared location by `rpi-persistent-shared-init`, before the bind mounts activate. Files are only pushed if missing from the destination. Existing files are never overwritten, so changes made at runtime are preserved. The exception is `StaticPath=` entries, which are removed from the shared location first and so are always replaced from the active slot. This means an OTA update can deliver new shared application data simply by including it in the rootfs - no separate data partition update is required.
