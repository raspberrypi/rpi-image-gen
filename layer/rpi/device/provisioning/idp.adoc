= IDP Layers

== Overview

The `rpi-idp` layer family provides Image Description Provisioning (IDP) configuration defaults for Raspberry Pi device images. These layers define attributes used in Provisioning Map (PMAP) templates, such as encryption parameters.

`rpi-idp` is the top-level layer, pulling in sub-layers via dependencies for each supported provisioning feature:

[cols="1,3"]
|===
| Layer | Purpose

| `rpi-idp-luks2` | Device scoped LUKS2 encrypted volume attributes

|===

Links to these layers can be found below.

== Layer Defaults vs. PMAP Authorship

The variables defined here are *defaults for convenience*. An image layout is in full control of its own PMAP and is not required to use them at all. The PMAP is a JSON fragment authored per-image; these variables are available to PMAP templates but each PMAP itself is independent. This means:

* An image with multiple LUKS containers can use different cipher parameters per volume by referencing different variables or hard-coding values directly in its PMAP template.
* A custom image can ignore these variables entirely.
* These variables are only meaningful when an image layout chooses to reference them.

See the link:../../../../provisioning/index.html[IDP Provisioning Documentation] for a full description of the PMAP format and how it is embedded in the IDP document.

[[provisioning-stores]]
== Provisioning stores (IDP 2.3.0)

A store is somewhere on the device that a provisioning tool can write per-device data to after flashing the image, for example OS customisation configuration or identity data. The image decides where its stores are, and the section for each purpose decides what goes in them.

A `filesystem` store's partition must have a mountpoint. On the device, the store's data is at that mountpoint followed by `location`.

[source,json]
----
"stores": {
  "customisation": { "type": "filesystem", "partition": "persistent", "location": "/" }
}
----

New purposes are added to the schema as minor versions, together with the section that describes their data. For example, identity data on a raw partition:

[source,json]
----
"stores": {
  "customisation": { "type": "filesystem", "partition": "persistent", "location": "/" },
  "identity": { "type": "raw", "partition": "provision" }
}
----

[[os-customisation]]
== OS customisation (IDP 2.3.0)

Describes how the image accepts a per-device OS customisation: the mechanism it runs determines the configuration a provisioning tool writes to the `customisation` store.

New mechanisms are added to the schema as minor versions.

A single-slot image, with the configuration on the boot partition:

[source,json]
----
"stores": {
  "customisation": { "type": "filesystem", "partition": "boot", "location": "/" }
},
"customisation": { "mechanism": "rpi-preseed" }
----

A slotted image, with the configuration on the persistent partition:

[source,json]
----
"stores": {
  "customisation": { "type": "filesystem", "partition": "persistent", "location": "/" }
},
"customisation": {
  "mechanism": "rpi-preseed",
  "rpi-preseed": { "domains": ["system", "user", "time", "locale"] }
}
----
=======

== Contributing to the IDP document

Layers can contribute to sections that the IDP schema marks as `"x-dropin": true` using drop-ins for `rpi-idp` in a directory named after the section, eg `for/rpi-idp/stores/`. Each file holds JSON for part of the section. A later layer's file replaces an earlier layer's file of the same name, and an empty file removes it. The remaining files are then merged in order: objects are merged, arrays are appended, and any other value from a later file replaces an earlier one. The result is validated against the schema.
